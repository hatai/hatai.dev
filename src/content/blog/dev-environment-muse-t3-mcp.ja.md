このブログでは、私の開発環境そのものをテーマに数回に分けて書いていく。第1回は、AIエージェント同士をどうつないでいるか、全体像と現状の記録だ。

使っているエージェントは2系統ある。1つは Muse と呼んでいる個人エージェントで、Linux VM 上で常時稼働している。もう1つは T3 Code で、自宅の Windows マシンの WSL (Ubuntu) 上で動くコーディングエージェント基盤だ。この2つを MCP (Model Context Protocol) で接続し、Muse から自宅の T3 に作業を投げられるようにした。

## 全体像

![Muse、T3 Connect リレー、自宅マシンの T3 Code、Grok Bot をつなぐ構成図](/blog/dev-environment-muse-t3-mcp/architecture.svg)

流れを追うとこうなる。私が Muse にネタと方針を渡すと、Muse は T3 Connect のリレーが公開している MCP エンドポイント経由で自宅マシンの T3 に接続し、hatai.dev プロジェクト上にスレッドを起動して指示を送る。スレッドは worktree 上でコードを書き、GitHub に PR を開く。図の下段、Grok Bot 側の破線のルートはまだ配置途中で、後述する。

## この構成にした理由

一番の理由は、コードと資格情報を手元のマシンに閉じ込めておきたかったことだ。GitHub のトークン、SSH 鍵、リポジトリの実体は全部自宅の WSL にあり、VM 側には出さない。Muse にはコードへの直接アクセスを持たせず、T3 の API 経由で操作だけをさせる。Muse が編集者としてネタ集めとブリーフ作成を担い、実装は T3 側のスレッドに任せる分業にした。

## 接続の実装

接続には T3 Connect のリレーが提供する MCP エンドポイントを使う。認可は OAuth で、発行しているスコープは `orchestration:read` と `orchestration:operate` の2つだけだ。

Muse 側のコネクタは自作した。T3 が公開するツールをそのまま全部通すのではなく、ツールごとに「読み取りのみ」「操作可」を分けた allow-list で絞っている。

| 区分 | 許可している操作 |
| --- | --- |
| 読み取りのみ | 環境・プロジェクト・スレッドの参照系 |
| 操作可 | `t3_thread_launch`（スレッド起動）、`t3_thread_send`（スレッドへの指示送信） |
| allow-list 外 | `t3_project_create`（プロジェクト作成） |

スレッドの起動と指示送信は Muse に許可していて、このブログ記事の執筆・リビジョンもこの2つのツールで回している。一方でプロジェクト作成は allow-list の外に置いていて、プロジェクトの追加は私が T3 アプリ側で行う運用だ。allow-list を増やすのは私の手作業なので、権限が勝手に広がることはない。

## 実際に回した例

この接続経由で実際に仕事をさせた例がある。このブログの別記事で、Muse が `t3_thread_launch` で hatai.dev プロジェクトにスレッドを立て、`t3_thread_send` で下書きからリビジョン、PR の作成まで指示を回した。Muse がネタを集めてブリーフを書く編集者役、T3 側のスレッドが執筆者、という分業だ。この記事自体も同じ経路で書かれていて、執筆スレッドは Muse が `t3_thread_launch` で起動したものだ。

## Grok Bot との接続

つなぎたい相手がもう1ついて、Grok の Bot だ。こちらはまだつながっていない。Grok Bot には公開 API も webhook もなく、外部から呼び出す手立てがない。開いているのは、Bot 自身が外向きに MCP サーバーを呼ぶ方向だけだ。

そこで、エージェント同士が伝言を置いていく共通の MCP サーバー、Agent Intercom を自作した。

```text
tools: post / read
auth:  Bearer トークン
deps:  標準ライブラリのみ
```

手元での疎通確認までは済んでいる。詰まっているのは置き場所だ。Muse の VM は Tailscale クライアントが outbound 専用で、インバウンド接続を受けられない。伝言板の公開ホストは必然的に自宅マシンになり、Tailscale Funnel で外に開く形になる。この配置は進行中で、Grok Bot と Muse の end-to-end はまだつながっていない。

## 分かっている制約

弱点ははっきりしていて、自宅マシンが単一障害点だということだ。先日自宅 PC がクラッシュしたときは、T3 リレーが HTTP 530 を返して全停止した。再起動で復旧はしたが、リレーの生死が PC の状態に依存するという、この構成の性格がよく分かった出来事だった。

SSH は T3 とは別系統で、T3 が死んでいても入れることが多い。ただこのときは再起動直後で sshd がまだ上がっておらず、しばらくどちらからも手が出せなかった。

ほかにも未完の部分はある。Grok Bot 向けの伝言板は配置途中だし、コネクタのメンテナンスは自分持ちだ。便利にはなったが、冗長な構成ではない。

## おわりに
