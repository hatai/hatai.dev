このブログでは、私の開発環境そのものをテーマに数回に分けて書いていく。第1回は、エージェント同士をどうつないでいるかだ。

エージェントは2系統ある。Muse と呼んでいる個人エージェントが Linux VM 上で常時動いていて、自宅の Windows マシンの WSL (Ubuntu) では T3 Code というコーディングエージェント基盤が動いている。この2つを MCP (Model Context Protocol) でつないだ。

## 全体像

![Muse、T3 Connect リレー、自宅マシンの T3 Code、Grok Bot をつなぐ構成図](/blog/dev-environment-muse-t3-mcp/architecture.svg)

私が Muse にネタと方針を渡す。Muse は T3 Connect のリレーが公開している MCP エンドポイント経由で自宅マシンの T3 に接続し、hatai.dev プロジェクト上にスレッドを起動して指示を送る。スレッドは worktree でコードを書いて、GitHub に PR を開く。図の下段、Grok Bot 側の破線はまだ配置途中で、後で書く。

## なぜつないだか

コーディングエージェントの作業は、私の確認待ちで止まる。私が確認できない間、ずっと止まったままだ。これをなんとかしたかった。

何を決めないといけないかを Muse が要約してくれると分かりやすい。自分が全部直接やるより、第3者視点で物事を進められるのがいい。

あと、コードと資格情報は手元に置いておきたかった。GitHub のトークン、SSH 鍵、リポジトリは全部自宅の WSL にある。VM 側の Muse にはコードへの直接アクセスを持たせず、T3 の API 経由で操作だけさせる。Muse は編集者、実装は T3 側のスレッド、という分業だ。

## 接続の実装

接続には T3 Connect のリレーが出している MCP エンドポイントを使う。認可は OAuth で、スコープは `orchestration:read` と `orchestration:operate` の2つだけだ。

コネクタは自作した。T3 が公開するツールをそのまま全部通すのではなく、ツールごとに allow-list で絞っている。

| 区分 | 許可している操作 |
| --- | --- |
| 読み取りのみ | 環境・プロジェクト・スレッドの参照系 |
| 操作可 | `t3_thread_launch`（スレッド起動）、`t3_thread_send`（スレッドへの指示送信） |
| allow-list 外 | `t3_project_create`（プロジェクト作成） |

スレッドの起動と指示送信は Muse に許可していて、このブログの執筆・リビジョンもこの2つで回っている。プロジェクト作成だけは外に置いていて、プロジェクトの追加は私が T3 アプリ側でやる運用だ。allow-list を増やすのは手作業なので、権限が勝手に広がることはない。

## つないで変わったこと

直接コーディングエージェントに指示することがかなり減った。

指揮役のコーディングエージェントを立てて、そいつがさらに作業者のコーディングエージェントに作業を振る仕組みが効いている。指揮役と Muse、それに Grok Bot がやりとりすることで、第3者としての意見や意思決定、改善案が出せる。

特に改善ループが一番のメリットかもしれない。私が細かい指示をしなくても、勝手にどんどん提案と実装・適用が進む。

このブログの別記事もこの仕組みで書いた。Muse が `t3_thread_launch` で hatai.dev プロジェクトにスレッドを立て、`t3_thread_send` で下書きからリビジョン、PR 作成まで指示を回した。この記事自体も同じで、執筆スレッドは Muse が起動したものだ。

## Grok Bot との接続

もう1つつなぎたい相手がいて、Grok の Bot だ。理由は保険だ。どっちかがリミットで作業が止まったとき、もう片方に逃がせる。止まっている間に片方だけで進めた意思決定を、あとで伝達もしやすい。

ただ、Grok Bot には公開 API も webhook もなく、外から呼ぶ手立てがない。開いているのは、Bot 自身が外向きに MCP サーバーを呼ぶ方向だけだ。

なので、共通の MCP 伝言板 Agent Intercom を自作した。エージェント同士が伝言を置いていく掲示板だ。

```text
tools: post / read
auth:  Bearer トークン
deps:  標準ライブラリのみ
```

手元での疎通は済んでいる。詰まっているのは置き場所だ。Muse の VM は Tailscale クライアントが outbound 専用で、インバウンド接続を受けられない。伝言板の公開ホストは自宅マシンになって、Tailscale Funnel で外に開く形になる。ここはまだ進行中で、Grok Bot と Muse の end-to-end はつながっていない。

## 不満と不安

実装を全部ローカルでやっているから、マシンが落ちたら全部止まる。実際落ちた。自宅 PC がクラッシュした日、T3 リレーが HTTP 530 を返して全部止まった。再起動で復旧したが、自宅マシンが単一障害点なのがよく分かった。SSH は T3 とは別系統なんだが、そのときは再起動直後で sshd がまだ上がっておらず、しばらくどちらからも手が出せなかった。

ただ、T3 は落ちても、作業途中のスレッドに「再開しろ」ってメッセージを自動で送ってくれる。そこはいい感じだ。

もう1つある。本当に期待している方向に進んでいるのかの把握は難しい。これは人間相手でも一緒だが。AI Bot をフル活用しているからこその可視化する手段はあると思うんだけど、どうするとベストなのかはまだわかっていない。

## おわりに

自宅マシンをハブにして、エージェント同士を MCP でつなぐところまでは来た。まだ建設途中だ。

この記事の作られ方も、この環境の一部だ。テーマを選んだのは Muse で、私に「なぜつないだか」「何が変わったか」「困りごとは何か」とインタビューして、その回答を素材に T3 の執筆スレッドが書いた。最初はブリーフだけで自動生成していたんだが、初稿は内容が薄くて、文体も自分と違った。なのでネタ探しと執筆の間にインタビューの工程を足す形に、生成の仕組み自体を変えた。今後も週1で「ネタ探し→インタビュー→執筆」の流れで回していく。

エージェントに書かせるにも、人の判断と声を入れる工程は要る。この1本でそれがよく分かった。
