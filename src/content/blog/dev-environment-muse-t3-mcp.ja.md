## 困っていたこと

Coding Agent に作業を任せると、「私の確認待ち」で止まる場面が増えた。私が見ていない間、作業は止まったままになる。エージェントが速くなっても、判断待ちの列が詰まれば全体は進まない。

そこで、常駐している個人 AI エージェントの [Muse](https://muse.ai) と、自宅マシンの [T3 Code](https://t3.codes) をつないだ。決めるべきことを Muse が要約して持ってくる。私が見るのは要約と判断点だけになる。第3者の視点で物事を進めてくれるのも大きかった。

## 構成

Muse は Linux の VM 上にいる。T3 Code は自宅の Windows マシンの中で、WSL の Ubuntu 上で動いている。この2つを T3 Connect のリレーを経由して MCP でつないだ。認可は OAuth で、スコープは orchestration:read と orchestration:operate。

![構成図](/blog/dev-environment-muse-t3-mcp/architecture.svg)

接続は自作のコネクタで、ツールごとに allow-list を分けている。読み取り系と、スレッドの起動・指示送信のような操作系は許可。プロジェクトの作成は対象外にしてあって、それは T3 Code のアプリで私がやる。エージェントに渡す操作は、最初から絞っておきたかった。

## 何が変わったか

直接 Coding Agent に指示する事がかなり減った。

いまは指揮役の Coding Agent を立ててあって、そいつが作業者の Coding Agent に作業を振る。指揮役と Muse がやりとりするので、第3者としての意見や意思決定、改善案が出てくる。

一番のメリットは改善ループだと思う。私が細かい指示をしなくても、提案と実装・適用が勝手にどんどん進む。今日このブログの記事が PR になっているのも、その流れの中で起きたことだ。

## Grok Bot ともつなぎたい

指揮役はもともと Grok Bot が担当している。ただ Grok Bot には公開 API も webhook もない。外から叩けるのは、Bot が外向きに MCP サーバーを呼ぶ方向だけだった。

なので共通の伝言板を置くことにした。MCP サーバーを自作して、手元では投稿と読み取りの疎通まで確認した。狙いは保険だ。どっちかが使用量のリミットで止まったとき、止まっている間に片方だけで進めた意思決定を、もう片方が拾えるようにしておきたい。

ただ、まだ end-to-end ではつながっていない。Muse の VM は外からの接続を受けられない（Tailscale のクライアントが外向き専用）ので、伝言板の公開ホストは自宅マシンに置く必要がある。そこは進行中。

## 落ちる話

実装は全部ローカルでやっている。マシンが落ちたら全部止まる。実際に先日、自宅の PC がクラッシュして、T3 Connect のリレーが HTTP 530 を返し、全停止した。

ただ T3 Code は復旧したとき、作業途中だったスレッドに「再開しろ」というメッセージを自動で送ってくれる。落ちても続きから戻ってくる感じは、思ったよりいい。

## まだ分かっていないこと

本当に期待している方向に進んでいるのか、把握が難しい。これは人間相手でも一緒だと思う。ただ、AI Bot をここまでフル活用しているなら、それに合った可視化の手段はあるはずだと思っている。どうするのがベストなのかは、まだ分かっていない。
