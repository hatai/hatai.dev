> この記事は、本文で紹介しているエージェントチームの開発フローで AI が下書きを作成し、人間（筆者）が内容の確認と修正を行ったものです。

個人開発中のサービス Pelway を、複数の AI エージェントに役割を分けて開発しています。指揮役・実装・レビュー・マージを別のエージェントが担い、私は判断点だけを見る形です。この記事では、そのフローの仕組みと、実際に回してみて分かったメリットと摩擦を書きます。

Pelway 自体は、タスクごとに Linux コンテナの sandbox を立ててジョブを実行する設計のサービスです。まだ本番には出ていませんが、開発フローの方はすでに回っていて、こちらの方が記事にする価値がありそうだったので先に書きます。

## フローの全体像

![タスクが Issue からマージまで流れる過程と各段階の担当](/img/agent-team-flow.ja.svg)

用語メモ: 「着手OKの合図」は、人間が Issue に付ける `ready-for-agent` というラベルのことです。sub-issue は親 Issue にぶら下がる子タスク、worktree は Git の作業コピーを別ディレクトリに分ける仕組み、Kodiak はマージ待ち行列を管理するツールです。

役割分担は次のとおりです。

| 役割 | 担当 | やること |
| --- | --- | --- |
| 指揮役 | Grok Bot（代行は Claude バックグラウンドセッション） | Issue の整理、実装スレッドへの指示、レビュー結果の取りまとめ |
| 実装 | GLM（T3 Code 上のスレッド） | Issue 単位の実装と、固定形式の実装者メモ |
| レビュー | Codex（セカンドレビューは Claude） | PR のレビュー。高リスク PR と通常 PR のサンプルに Claude を追加 |
| マージ | Kodiak（ホスト型のマージキューツール） | 通過した PR の取り込み |
| 判断 | 人間（私） | ready-for-agent を付ける、マージする、方向を決める、の 3 点だけ |

指揮役が週間セッションリミットで止まる間は Claude が代行し、その引き継ぎ手順は仕様書と runbook に正本化してあります。

![指揮役が停止したときの例外経路: runbook に沿って Claude が代行する](/img/conductor-failover.ja.svg)

タスクは次の順に流れます。Issue を起票し、分割できるものは sub-issue に分けます。私が「着手OK」の合図である ready-for-agent ラベルを付けると、指揮役が GLM の実装スレッドへ割り振り、出来上がった PR を Codex がレビューし、通ったものがマージキューに入ってマージされます。

## 工夫している仕組み

再現に効きそうな部品を 4 つ挙げます。

**正本化**: 引き継ぎ手順・役割分担・運用ルールは、仕様書・runbook・AGENTS.md・共有スキルに書きます。エージェントの記憶はセッションを跨がないので、書かないと消えます。人間向けメッセージで Issue や PR の番号を必ずフル URL リンクにする、という細かいルールも仕組み化しました。開発スキルには [mattpocock/skills](https://github.com/mattpocock/skills) を採用しています。

**実装者メモ**: GLM スレッドが毎回残す固定形式のメモです。項目は詰まった点・曖昧さ・前提・不足・スキルや AGENTS.md への提案です。骨格は次の形です。

```
## 実装者メモ
- 詰まった点:
- 曖昧さ:
- 前提:
- 不足:
- スキル・AGENTS.md への提案:
```

このメモがあると、指揮役がコンテキストを持たなくても次の指示を出せます。

**レビューの明記**: レビュー結果には担当・モデル名・effort を定型で明記させます。どのモデルのどの effort に回すかは、PR の内容（サイズ・変更パス・ラベル・修正の往復回数）で振り分けます。

**マージキューの分離**: GLM の実装枠がマージ待ちで詰まるのを避けるため、マージ処理を実装枠から独立させて Kodiak に任せました。

## メリットと摩擦（観測）

回してみて分かったことです。推測ではなく実際に起きたことだけを書きます。

| 観点 | メリット | デメリット・摩擦 |
| --- | --- | --- |
| 並列性 | 実装・レビュー・調査を並列に回せ、1 件のレビュー待ちで全体が止まらない | 律速は消えずに移動し、実装が速くなるとレビューとマージキューが詰まる |
| 正本 | 決定が ADR・仕様書・共有スキルに残り、長い前提説明が要らない | ルールは書かないと消え、維持コストが常時かかる |
| 分業 | モデルの得手で割れる（実装は GLM、レビューは Codex、セカンドオピニオンは Claude） | 複数サブスクリプションの使用量制限を同時に管理する必要がある |
| 人間の負荷 | 判断点だけに集中できる | 指揮役が単一障害点で、セッションリミットで止まる |

対策として、指揮役の代行手順は runbook 化し、GLM 枠の詰まり対策にマージキューを実装枠から独立させました。ただ、手順があっても排他は保証されず、本役と代行が同じ PR を同時にレビューする二重指揮が実際に起きました。詰まる場所が変わっただけで律速そのものは残っていますし、正本を書き続ける手間は結構重いです。

![律速の位置が実装、レビュー、マージキューへ移動していく様子](/img/bottleneck-moves.ja.svg)

## 成果物の一例: ADR 0012

このフローから出てきた成果物の一例を挙げます。本番トポロジを定めた ADR 0012 で、Issue 起票 → ready-for-agent → GLM が実装（ADR 本文と、実在とリンク解決を検査する構造テスト）→ Codex がレビュー、という経路をそのまま通ってきました。

以下は ADR の内容をこの記事用に編集した抜粋です（原典は公開リポジトリ Pelway の `docs/adr/0012-production-topology-single-host.md` です）。

> **背景**: Pelway の本番配置の設計方針を先に決めるための ADR。実際のホスティング契約や配置作業、compose ファイルの作成は対象外と明記してある。選んだ理由は、運用を単純に保てることと、止まったときに自分で全部見られる構成にしたかったから。
>
> **決めたこと**: 本番は単一ホスト。構成要素は Docker Compose で宣言し、公開入口はリバースプロキシの Caddy 1 本、ホスト運用の定期ジョブ（バックアップ・ヘルスチェック・セキュリティ更新）は systemd タイマーで回す。ネットワークは edge・app・data・sandbox に分け、Postgres は `data` にだけ置いて `ports` を持たせないので、sandbox から DB への到達経路がない。ホスティングは国内前提で、マネージド DB やオブジェクトストレージのようなクラウド固有サービスには依存しない。ファイアウォールや SSH の硬直化、自動更新といったホストの堅牢化はスクリプトと設定としてリポジトリで管理する。雛形には Rakazo のセルフホスト構成を採用した。
>
> **見送った案と代償**: Kubernetes は初期規模には過剰として不採用。規模が必要になった時点で移行設計を別に立てる。クラウド固有サービスを外した代償として、バックアップ・更新・監視まわりの運用部品は compose ファイルやスクリプトとして自分で書く必要があり、その作成は別 Issue に積んでいる。

このフロー自体も変わっていくはずなので、変わったらまた書きます。質問があれば [me@hatai.dev](mailto:me@hatai.dev) へどうぞ。
