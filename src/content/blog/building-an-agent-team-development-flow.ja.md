個人開発中のサービス Pelway を、複数の AI エージェントに役割を分けて開発しています。指揮役・実装・レビュー・マージを別のエージェントが担い、私は判断点だけを見る形です。この記事では、そのフローの仕組みと、実際に回してみて分かったメリットと摩擦を書きます。

Pelway 自体は、タスクごとに Linux コンテナの sandbox を立ててジョブを実行する設計のサービスです。まだ本番には出ていませんが、開発フローの方はすでに回っていて、こちらの方が記事にする価値がありそうだったので先に書きます。

## フローの全体像

役割は次のように分けています。

- **指揮役**: Grok Bot が本役です。Issue の整理、実装スレッドへの指示、レビュー結果の取りまとめをやります。週間セッションリミットで止まる間は Claude のバックグラウンドセッションが代行し、その引き継ぎ手順は仕様書と runbook に正本化してあります。
- **実装**: T3 Code 上の GLM スレッドです。Issue 単位でスレッドを立てて実装し、毎回固定形式の実装者メモを残します。
- **レビュー**: Codex が主担当です。高リスクの PR と、通常 PR のサンプルには Claude のセカンドレビューを付けます。
- **マージ**: ホスト型のマージキュー Kodiak を採用しています（[Issue #300](https://github.com/hatai/Pelway/issues/300)）。
- **人間（私）**: 「ready-for-agent ラベルを付ける」「マージする」「方向を決める」の 3 点だけです。

タスクは次の順に流れます。Issue を起票し、分割できるものは sub-issue に分けます。私が ready-for-agent を付けると、指揮役が GLM の実装スレッドへ割り振り、出来上がった PR を Codex がレビューし、通ったものがマージキューに入ってマージされます。

## 工夫している仕組み

再現に効きそうな部品を 4 つ挙げます。

**正本化**: 引き継ぎ手順・役割分担・運用ルールは、仕様書・runbook・AGENTS.md・共有スキルに書きます。エージェントの記憶はセッションを跨がないので、書かないと消えます。人間向けメッセージで Issue や PR の番号を必ずフル URL リンクにする、という細かいルールも仕組み化しました（[Issue #303](https://github.com/hatai/Pelway/issues/303)）。開発スキルには [mattpocock/skills](https://github.com/mattpocock/skills) を採用しています。

**実装者メモ**: GLM スレッドが毎回残す固定形式のメモです。項目は詰まった点・曖昧さ・前提・不足・スキルや AGENTS.md への提案です。骨格は次の形です。

```
## 実装者メモ
- 詰まった点:
- 曖昧さ:
- 前提:
- 不足:
- スキル・AGENTS.md への提案:
```

このメモがあると、指揮役がコンテキストを持たなくても次の指示を出せます。

**レビューの明記**: レビュー結果には担当・モデル名・effort を定型で明記させます。どのモデルのどの effort に回すかは、PR の内容（サイズ・変更パス・ラベル・修正の往復回数）で振り分けます。

**マージキューの分離**: GLM の実装枠がマージ待ちで詰まるのを避けるため、マージ処理を実装枠から独立させて Kodiak に任せました。

## メリット（観測）

回してみて分かったことです。推測ではなく実際に起きたことだけを書きます。

- 実装・レビュー・調査を並列に回せます。1 件のレビュー待ちで全体が止まる、という状態がなくなりました。
- 決定が ADR・仕様書・共有スキルに正本として残るので、エージェント間で長い前提説明をやり直さなくて済みます。
- モデルの得手で分業できています。実装量は GLM、レビューは Codex、セカンドオピニオンは Claude という分担です。
- 私の作業が判断点だけに絞られました。

## デメリットと対策

摩擦もちゃんとあります。

- **指揮役が単一障害点**: セッションリミットで止まります。代行手順を runbook 化したのですが、本役と代行が同じ PR（[#155](https://github.com/hatai/Pelway/pull/155)）を同時にレビューする二重指揮が実際に起きました。手順があっても排他までは保証されない、という課題が残っています。
- **ボトルネックは消えずに移動する**: 実装が速くなると、レビューとマージキューの詰まりが新しい律速になりました。GLM 枠の詰まり対策としてマージキューを独立させましたが、詰まる場所が変わっただけで、律速そのものは残っています。
- **正本の維持コスト**: ルールは仕様書・スキル・AGENTS.md に書かないと消えます。書き続ける手間が常時かかり、これは結構重いです。
- **使用量制限の同時管理**: 複数のサブスクリプションの枠を同時に見る必要があり、どこかが枯渇すると全体がその枠に律速されます。

## 成果物の一例: ADR 0012

このフローから出てきた成果物の一例を挙げます。本番トポロジを「Docker Compose＋リバースプロキシ（Caddy）＋systemd タイマーの単一ホスト構成」に定めた ADR 0012 です（[PR #429](https://github.com/hatai/Pelway/pull/429)）。

内容は、ネットワークを edge・app・data・sandbox に分け、Postgres は sandbox から到達不能にするというものです。Issue として起票され、ready-for-agent → GLM が実装（ADR 本文と、実在とリンク解決を検査する構造テスト）→ Codex がレビュー、というこのフローの経路をそのまま通ってきました。

## 再現するならここから

同じようなフローを組むなら、私ならこの順で整えます。

- [ ] 役割を 1 エージェント 1 役に分け、担当・モデル・effort を明記する運用にする
- [ ] 引き継ぎ・役割・運用ルールの正本をリポジトリ内の文書（仕様書・runbook・AGENTS.md）に置く
- [ ] Issue は分割できるものは分割し、エージェントへの投入口のラベルを 1 つにする
- [ ] 実装メモの固定形式を決めて毎回残させる
- [ ] レビュー担当を実装担当と別にし、セカンドレビューを付ける条件を決める
- [ ] マージキューを実装枠から独立させる
- [ ] 人間の判断点を列挙して絞る
- [ ] 指揮役が止まったときの代行手順を runbook に書く

このフロー自体も変わっていくはずなので、変わったらまた書きます。質問があれば [me@hatai.dev](mailto:me@hatai.dev) へどうぞ。
